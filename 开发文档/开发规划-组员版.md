# 协作工作台 团队任务与代码协同系统1.0 开发规划

文档版本：0.1　编写日期：2026年10月24日　适用读者：组长、组员、指导教师。

本项目开发 Windows 客户端，帮助私有项目中的成员分配任务、跟踪进展、提交验收，并在本地管理 Git 仓库。核心交付是协作与代码管理；个人 AI 辅助安排在后期，时间不足时优先延期。项目名称中的“1.0”是产品目标版本，不表示系统已经开发完成。

本规划依据三轮问答制定，按模块安排逐版功能和检查方式。已经确认的需求与为便于开发而提出的执行建议分开记录；本文件和《开发执行说明-AI版》使用相同的功能编号、版本与业务规则。

## 一 已确认的方向

- 直接开发 Windows 客户端，采用 Electron + Vue 3；Spring Boot + MySQL 提供共享服务。Vue 是客户端里的界面技术，无须另交付独立网站。
- 先在本地完成和联调，再考虑迁移共享服务到云端。四个客户端应连接同一个后端，不能各用独立数据库代替协作。
- 一个用户可参加多个私有项目，只有项目成员可查看项目数据，组长权限限定在所属项目内。
- 只有组长可以发布、指派任务。成员可领取开放任务；每个任务只有一名负责人，并发领取只能一人成功。
- 成员提交验收后，由组长最终决定通过或退回。其他成员可以受托复核并提意见，不因此获得最终验收权。
- 支持任务截止时间、项目动态、个人未读提醒；关闭窗口时询问退出还是后台常驻。
- 支持输入 GitHub 地址、选择目录、克隆并显示进度，以及导入已有仓库、本地文件树、个人备注、提交、推送、拉取和任务分支。
- 备注仅保存在本机，不随仓库共享；文件改名后的重新关联可延后。
- AI 由每人自己的客户端调用个人配置的服务，密钥不进入项目共享后端，不提供项目共用 API 额度。
- 取消附件共享、在线公告编辑、聊天和答辩模拟；暂不引入 Python、LangChain、Redis、MCP 或工具调用 Agent。

来源以《问答-第三轮.md》为最新依据；更早问答中与之冲突的设想不再沿用。

## 二 为开发采用的初步安排

以下为规划建议，不应被描述为老师要求或小组已经逐项确认：

| 项目 | 本规划采用的建议 |
| --- | --- |
| 仓库结构 | 先使用一个 GitHub 仓库，客户端和服务端放在不同目录；一个协作项目先绑定一个远程仓库 |
| 注册与邀请 | 0.2 完成账号注册、登录和项目邀请；开发联调可先用四个演示账号，不把演示账号当成最终注册功能 |
| 成员角色 | 项目内仅组长和组员；邀请可由可撤销、可过期的项目邀请码完成 |
| 通知方式 | 0.3 先查询最新动态，0.5 再增加 WebSocket 实时更新与未读提示 |
| Git 起点 | 调用成员机器已安装的 Git，先支持常规单仓库，不开发完整代码编辑器与冲突编辑器 |
| 复杂合并 | 初版说明原因并引导用现有工具处理，不自动强推、不自动解决内容冲突 |
| 版本节奏 | 以可演示成果推进，暂不承诺日历工期；老师正式截止日期仍待核实 |

前后端“分离”和“分仓”不同：前者是客户端界面与共享业务的职责分开，后者是代码分别存放在两个 Git 仓库。初版可在同一仓库中放置 `desktop/`、`server/`、`docs/`，既保持职责分离，也减少维护多个仓库的成本。这个客户端协助管理其他项目时，初版也按一个项目一个仓库设计；支持多仓库可后续扩展。

## 三 使用过程和数据放在哪里

成员安装客户端后，可克隆或打开本地仓库，并配置自己的 Git 作者信息。需要共享任务时登录本系统，创建项目或通过邀请加入，绑定该项目对应的本地仓库。登录本系统、Git 提交作者身份、GitHub 访问认证和个人模型 API 配置是四件不同的事。

组长发布有截止时间的任务，可指定负责人或开放领取。负责人开始工作时使用任务分支，完成修改后选择文件并本地提交，再按需要推送。负责人在系统中提交验收，组长可以自行检查，也可请其他成员复核，最终通过或退回。上述操作留下动态，贡献页面展示任务与验收事实。

| 数据或操作 | 位置 | 是否在项目成员之间共享 |
| --- | --- | --- |
| 系统账号、成员关系、任务、截止时间、验收、动态与未读状态 | Spring Boot 共享服务和 MySQL | 按项目权限共享；个人未读状态分别保存 |
| 本地目录、工作区绑定、文件备注 | 本人客户端的数据目录 | 不共享，不默认提交 Git |
| 源代码、Git 分支与本地提交 | 本人选择的仓库 | 只有推送到远程后，其他人才能通过 Git 获取 |
| GitHub 访问凭据 | 本机已有 Git 凭据机制 | 不进入协作后端 |
| 模型 API 密钥、对话设置 | 本人客户端 | 不进入协作后端、不供组内共用 |

组长管理项目业务，不因此能读取他人的本地文件、备注、API 密钥或 Git 凭据。

## 四 模块与版本安排

版本号表示本项目的开发里程碑，各模块在同一个版本中共同形成演示成果。0.x 是开发版，1.0 是核心功能验收目标；0.6 的 AI 可延期，但不能将尚未完成的 AI 标为已经实现。

### F01 客户端与设置

| 版本 | 要做的内容 | 如何检查 |
| --- | --- | --- |
| 0.1 | Windows 窗口、项目与工作区导航、设置页；共享服务地址可配置 | 打开客户端，修改地址，关闭重开后仍保留 |
| 0.5 | 关闭窗口时选择退出或保留后台；托盘可恢复窗口与彻底退出 | 两条路径都能实际完成，不留下误以为退出的后台进程 |
| 1.0 | 打包安装与运行说明，检查客户端升级后的本地数据保留 | 在另一台目标 Windows 机器安装并运行 |

### F02 账号与私有项目

| 版本 | 要做的内容 | 如何检查 |
| --- | --- | --- |
| 0.2 | 注册、登录、退出、项目创建、项目邀请、成员列表、多项目切换 | 两人加入同一项目；未受邀账号直接请求数据也被拒绝 |
| 0.3 | 组长成员管理；移除成员时先处理其未完成任务；角色在项目内生效 | 同一人在不同项目可有不同角色，移除后不能继续接收该项目数据 |
| 1.0 | 登录失效处理、权限回归和数据备份恢复演练 | 失效登录不可继续写任务；恢复后数据与权限一致 |

组长转让、注销账号、找回密码的交付范围列为后续确认项，不把“组长完全控制”解释成无限的账号管理权限。

### F03 任务 分配与验收

| 版本 | 要做的内容 | 如何检查 |
| --- | --- | --- |
| 0.3 | 发布、指派、领取、开始、截止时间、提交验收、通过、退回、复核意见 | 两人抢同一任务仅一人成功；组员无法发布或最终验收 |
| 0.4 | 关联任务分支，验收时提醒本地未提交改动；保留任务与 Git 流程的区别 | 工作区脏状态会提示；提示不等于自动提交或验收通过 |
| 1.0 | 修改截止时间、重新指派和取消操作均留痕；完成状态与审核结果一致 | 退回保留原因和原负责人，历史完成记录不被静默抹去 |

建议状态：待领取、已指派、进行中、待验收、已完成、已取消。截止时间用于计算“即将到期／已逾期”，不额外变成一种工作状态。成员只能处理自己的任务；组长的重新指派或取消应说明原因并保留记录。

委派复核只收集意见，最终通过或退回由组长执行。复核者不是第二负责人，也不代表允许多人共同领取一个任务。任务负责人可在组外沟通，但系统不设置多负责人字段。

### F04 系统动态与贡献记录

| 版本 | 要做的内容 | 如何检查 |
| --- | --- | --- |
| 0.3 | 自动记录发布、指派、领取、开始、提交验收、退回、通过、复核和取消等操作 | 刷新或重启后仍能按时间查看记录 |
| 0.5 | 展示个人当前负责、待验收、已验收及复核记录；支持项目内筛选 | 不把待验收算作已验收，不用提交数量自动给贡献分 |
| 1.0 | 检查历史归属，区分原负责人、当前负责人和实际验收者 | 任务转交后，之前成员的活动记录仍可追溯 |

### F05 克隆 仓库与 Git 身份

| 版本 | 要做的内容 | 如何检查 |
| --- | --- | --- |
| 0.1 | 导入已有仓库，检查 Git 是否可用；展示当前分支与工作区状态 | 非仓库、无 Git、路径无效时给出明确提示 |
| 0.4 | 输入 GitHub 地址、选目标目录、克隆、显示阶段与可获得的实际进度；设置仓库级 Git 姓名和邮箱 | 成功后进入目录树；失败或取消后不把目录误标为成功仓库 |
| 1.0 | 检查私有仓库认证失败、网络中断、目录已存在等场景 | 不覆盖已有文件，提示原因和可行下一步 |

Git 姓名和邮箱是提交作者信息，不是 GitHub 推送密码。初版优先使用本机 Git 已有认证方式，并在缺少认证时提供引导；不自行开发完整 OAuth 登录平台，也不把密码直接写进远程地址。界面里分别展示系统登录状态、作者配置状态和仓库访问错误。

### F06 文件树与本地备注

| 版本 | 要做的内容 | 如何检查 |
| --- | --- | --- |
| 0.1 | 展示仓库目录，按工作区和相对路径保存人工备注 | 同名文件位于不同目录时备注不串，重启后仍存在 |
| 1.0 | 目录刷新、文件消失提示、大目录按需展开 | 不扫描和展示整个 `.git` 内部对象树，不把备注写入代码 |
| 后续 | 文件改名后的手动重新关联、多仓库项目 | 当前不承诺自动追踪文件改名 |

文件改名后旧路径的备注可保留为失效记录，初版允许在新路径重新填写，不必先实现重关联界面。

### F07 任务分支与 Git 操作

| 版本 | 要做的内容 | 如何检查 |
| --- | --- | --- |
| 0.4 | 为任务创建或关联分支；查看改动、选择文件、填写提交说明、本地提交、推送、获取远程信息和受限拉取 | 每次写操作前确认仓库、分支与操作对象；只提交选中文件 |
| 0.5 | 改进分支落后、分叉、未提交改动和推送被拒绝的解释；任务关联提交标识 | 不把操作失败显示成任务失败或验收通过，不自动强推 |
| 后续 | 客户端内图形化冲突解决、复杂合并、合并请求自动化 | 当前使用 GitHub 或已有 Git 工具处理复杂整合 |

候选初版拉取只允许工作区满足条件且可快进的情况；遇到分叉等复杂状态停止并说明原因。任务分支推送后，组长可在 GitHub 检查与合并；“代码已经合并”和“任务验收通过”是两个状态，初版不自动绑定。

任务状态只能说明谁负责哪个任务，不能物理阻止成员在外部编辑同一文件。任务分支和状态提醒减少冲突机会，不保证没有冲突。

### F08 实时提醒与截止提示

| 版本 | 要做的内容 | 如何检查 |
| --- | --- | --- |
| 0.3 | 进入项目时获取最新动态，按截止时间显示到期情况 | 系统重启后仍能正确计算逾期，不只靠本机定时器 |
| 0.5 | WebSocket 在线更新、个人未读、重连后补查、后台常驻提示 | 两个客户端看到同一变更；断线期间的记录重连后可查看 |
| 1.0 | 到期提醒去重，退出后台后不承诺继续接收通知 | 同一提醒不会因反复重连无休止重复出现 |

执行建议：截止时间可为空；提醒提前量先设可调整的默认值，最终数值在使用时确认。后台常驻依赖客户端进程和网络仍运行，不是离线推送服务。

### F09 个人 AI 辅助

| 版本 | 要做的内容 | 如何检查 |
| --- | --- | --- |
| 0.6 可延期 | 个人服务地址、模型和密钥设置，简单对话与任务描述分析，超时与失败提示 | 请求由本机发往个人模型服务；协作后端和其他组员看不到密钥 |
| 0.6 可延期 | 可将结果复制为任务描述草稿，由组长编辑并确认发布 | AI 回复不会直接新增任务、执行 Git 或改变状态 |
| 后续 | 本地模型服务、MCP、工具调用等研究 | 可参考 AstrBot，但不将其作为本期依赖 |

首个适配器建议只支持实际验证过的一类模型接口。密钥采用操作系统支持的本地加密存储；加密不可用时不静默保存明文。是否保存聊天历史、支持哪些模型服务在实际接入前再确认。AI 故障不能阻止协作和 Git 功能。

### F10 测试 部署与课程交付

| 版本 | 要做的内容 | 如何检查 |
| --- | --- | --- |
| 0.1 起 | 保留环境示例和运行记录，不把密钥写入仓库 | 组员能根据说明找到启动步骤 |
| 每一版 | 更新模块完成情况、测试证据和变更记录 | 未完成内容写明，不把界面占位当实现 |
| 1.0 | 安装包、源代码、数据库初始化与迁移脚本、运行说明、测试记录和演示流程 | 两台机器连接同一服务完成协作；本地 Git 在各自仓库生效 |
| 后续 | 云部署、自动更新、更多平台 | 当前先做好服务地址和环境配置，服务器系统与购买方案暂不定 |

## 五 推荐实施顺序与阶段检查

| 里程碑 | 优先成果 | 进入下一阶段前的检查 |
| --- | --- | --- |
| 0.1 | 客户端可运行，打开仓库，文件树与备注 | 在 Windows 实际打开，仓库和个人备注不混用 |
| 0.2 | 账号与私有项目 | 非成员直接访问被拒绝，不仅是页面隐藏 |
| 0.3 | 任务全流程、截止时间、动态 | 并发领取、越权、退回重提均验证 |
| 0.4 | 克隆、作者设置、任务分支、提交推送拉取 | 临时测试仓库中检查成功与失败，不先拿唯一课程仓库试危险场景 |
| 0.5 | 实时、未读、托盘和贡献展示 | 两端联调，断线重连，真正退出与后台运行区分清楚 |
| 0.6 | 可延期的个人 AI | 不共用额度，不影响核心流程，无自动执行 |
| 1.0 | 核心验收与课程材料 | 关键功能实测，已知问题记录，成员能解释自己负责的内容 |

## 六 四人协作的建议分工

以下是待组内确认的安排，不代表成员已同意或已具备对应能力。

| 成员代号 | 建议责任 | 每版可交付的证据 |
| --- | --- | --- |
| 一号 组长 | 需求取舍、架构与联调、任务验收、合并审核 | 决策记录、通过与退回原因、可运行演示 |
| 二号 | 任务与项目界面、交互原型 | 页面成果、对应功能编号、操作演示 |
| 三号 | 项目权限、任务服务、数据库 | 接口与迁移脚本、权限及状态测试 |
| 四号 | 测试、模型图、部署说明；能力允许时承担文件树或设置模块 | 用例与测试记录、图源文件、复现说明 |

各人使用任务分支，合并前说明功能编号、改动、验证方法和未解决问题。可以使用 AI，但提交者要能解释代码和重现验证，不能把同一模块同时交给多人或多个 AI 在同一分支无序覆盖。

## 七 验收时必须能展示的场景

1. 未加入项目的账号不能读取项目任务；组员不能通过直接请求发布或最终验收任务。
2. 两个成员同时领取同一任务，只能一人成功，负责人和动态记录一致。
3. 成员提交验收，组长可委派复核；复核意见不自动完成任务，组长退回后原负责人可继续并重新提交。
4. 输入 GitHub 地址克隆，显示真实阶段与进度；作者邮箱与 GitHub 认证分开说明。
5. 每个任务关联分支，选择文件本地提交、推送、符合条件时拉取；失败时保留文件并解释状态。
6. 本地备注在重启后保留，不出现在其他成员客户端；未提交改动提示不自动阻止或替代人工验收。
7. 在线实时更新；断线后的动态可补查；关闭窗口的退出和后台选项都有效。
8. 若交付 AI，使用各自密钥从客户端请求，回复经人确认采用；若延期，在交付说明中明确列出。

尚无实测的响应时间、内存或服务器承载量不写成已达指标。最终性能目标、正式截止日期与学校完整提交清单，待老师要求和原型测量后补充。

## 八 本轮剩余确认事项

这些问题不阻碍先编写构思文档和推进基础设计，也不另开固定第四轮：单项目单仓库建议是否足够；注册与邀请流程是否采用本规划；成员移除与组长转让的最终范围；到期提醒提前量；Windows 目标版本与演示网络；AI 支持的首个接口和聊天保存方式。遇到对应阶段时，带着可比较的方案再确认。
