# 协作工作台 团队任务与代码协同系统1.0 开发执行说明

文档版本：0.1　日期：2026年10月24日　读者：接手实现、测试、修复和复核的 AI 开发助手。

目标是按模块、按版本实现 Windows 私有项目协作客户端。配套《开发规划-组员版.md》说明业务和验收，本文件说明执行边界、契约候选和任务切片；两份文档不能被解释成已存在的代码。当前尚未开始产品实现。

## 1 使用约定与决策等级

每次接手先读本文件、组员版、仓库实际状态、适用的 AGENTS.md 和已有进度记录。三轮问答中第三轮回答为最新用户决策；原《需求.md》仍是历史起点，不能覆盖新版范围。若文档与代码不一致，先确认真实状态并报告，不擅自把未实现功能记为完成。

- 已确认：Windows 客户端 C 路线；Electron + Vue 3、Spring Boot + MySQL；私有多项目；组长发布与最终验收；单任务单负责人；克隆及本地 Git；个人备注；客户端直连个人 AI；AI 优先延期。
- 执行建议：以下目录、字段、端点、状态名、版本切片、邀请码及单项目单仓库是为推进开发提供的初步设计，可在保持已确认行为和同步文档的前提下调整。
- 待确认：精确 Windows 版本、截止与性能指标、组长转让和账号恢复范围、AI 接口与历史、云端部署环境。不虚构结果，不因普通实现选择反复请求用户批准。

用户要求：不修改“文档-学校”内任何文件；开发文档放“文档-AI”，产品代码及 GitHub 提交内容放“code&github”。学校模板副本也保留，填写版另命名。不得读取、输出或提交真实密钥，不自动进行推送、发布或用户未授权的远程写入。本文规划了产品内 Git 按钮，不等于授权开发助手现在操作真实仓库。

## 2 架构与数据边界

建议单仓库布局如下；当前仅为计划，不要把目录示例当作已有文件。

```text
code&github/
  desktop/          Electron 主进程 preload Vue 3 页面 本地服务适配
  server/           Spring Boot 共享业务与持久化
  docs/             随代码提交的接口与运行说明
  tests/            适合跨组件的验证脚本或测试资料
  README.md
```

Electron 直接加载打包的 Vue 界面，不额外交付功能相同的独立网站。页面只调用明确的 preload 接口；文件、Git、个人 API 与密钥处理在本地可信模块执行。保持上下文隔离，不向页面暴露任意 shell、文件系统或通用命令执行接口。[Electron 进程模型](https://www.electronjs.org/docs/latest/tutorial/process-model)、[隔离要求](https://www.electronjs.org/docs/latest/tutorial/security)

共享后端只保存账号、项目成员、任务、复核、验收、动态与个人未读状态。MySQL 不存个人工作区绝对路径、备注、GitHub 凭据或模型密钥。Git 仓库及其认证由本机管理。AI 请求路径固定为“客户端本地模块 → 用户个人模型服务”，不由共享后端代调，不提供项目共用 API。

后端地址、数据库连接、客户端数据位置等外部化配置。先本地开发，双机联调时连接同一个服务；数据库端口不向普通客户端直接开放。后端迁云不应改变任务 API 和数据归属，但仍需部署与迁移检查。

本期不加入 Python、FastAPI、LangChain、Redis、工具调用 Agent、MCP、资料附件、公告编辑、完整聊天、答辩模拟、代码编辑器或图形化冲突解决。

## 3 领域模型与不变量

建议的核心实体如下，名称可按实现规范调整，不在需求构思阶段承诺全部数据库列名。

| 实体 | 核心数据 | 关键约束 |
| --- | --- | --- |
| User | id、系统登录标识、密码哈希、显示名 | 系统身份与 Git 作者及 GitHub 认证分离 |
| Project | id、名称、ownerId、repoUrl、状态 | 所有读写依据成员关系校验，默认私有 |
| Membership | projectId、userId、项目角色、成员状态 | 项目与用户组合唯一，角色只在该项目生效 |
| Invitation | projectId、邀请码摘要、过期时间、撤销状态 | 组长创建，校验后加入，不公开泄露成员资料 |
| Task | id、projectId、标题、描述、状态、assigneeId、dueAt、version | 最多一个负责人，领取和状态转换采用原子条件更新 |
| ReviewOpinion | taskId、提交轮次、复核者、意见、时间 | 委派复核不授予最终通过或退回权 |
| Acceptance | taskId、提交轮次、组长、结果、原因、时间 | 每次提交保留独立记录，退回不删除历史 |
| Activity | id、projectId、taskId、actorId、类型、变更摘要、时间 | 与业务修改在同一事务提交，不伪造成功事件 |
| Notification | userId、activityId、类型、readAt、去重标识 | 接收者与项目权限校验，个人已读相互独立 |
| LocalWorkspace | localId、当前系统账号范围、projectId、repoUrl、rootPath | 本机保存；同一机器不同系统账号不得误串绑定 |
| LocalNote | workspaceId、相对路径、备注 | 本机保存，不共享、不默认进仓库；路径不只用文件名 |
| LocalTaskBranch | workspaceId、taskId、branch、可选提交标识 | 是任务和仓库的本机关联，不用作者邮箱推断系统贡献 |

任务状态候选：

```text
OPEN -> ASSIGNED -> IN_PROGRESS -> IN_REVIEW -> DONE
OPEN -> IN_PROGRESS                         领取后直接开始的简化操作
IN_REVIEW -> IN_PROGRESS                    组长退回给原负责人
非终态 -> CANCELED                          组长说明原因并留痕
```

OPEN 不含负责人；ASSIGNED、IN_PROGRESS、IN_REVIEW、DONE 含一名负责人。创建任务时可开放领取或直接指派。负责人提交 IN_REVIEW 不等于 DONE。只有该项目组长执行最终验收；复核者只能向组长提交意见。dueAt 为空表示无截止；逾期是由服务器时间与终态计算的派生属性，不替代工作状态。存储统一时间点，客户端按用户时区显示，初期中文演示使用 Asia/Shanghai。

组长可调整指派、截止时间、取消未终结任务，并记录原因；不将“完全控制”扩展为读取成员密钥、清除历史或绕过 GitHub 权限。对已完成任务重新打开、组长转让等未确认规则，先不新增自动行为。

并发领取必须在服务端通过事务或条件更新保证一人成功；前端禁用按钮不算实现。状态更新使用版本条件，重复请求须避免重复验收及动态。验收、指派与成员移除操作处理竞争状态；移除成员前处理未完成任务，并使旧会话无法再订阅项目数据。任务分配不代表能够锁住仓库文件，也不承诺消灭重复开发。

## 4 接口契约候选

在 0.2 首次实现前冻结基础请求和错误格式，同步进代码随附文档。不先搭建微服务。以下路径是建议的契约起点。

| 模块 | HTTP 接口示例 | 必要行为 |
| --- | --- | --- |
| F02 | POST /api/auth/register、/login、/logout；GET /api/me | 服务端验证，密码哈希，登录失效明确处理 |
| F02 | GET/POST /api/projects；GET /api/projects/{p}/members | 登录用户仅可见自己的项目，创建者成为组长 |
| F02 | POST /api/projects/{p}/invitations；POST /api/invitations/join | 限组长邀请，过期撤销校验，加入操作原子化 |
| F03 | GET/POST /api/projects/{p}/tasks；PATCH /api/tasks/{t} | 仅组长发布和管理，防止跨项目对象访问 |
| F03 | POST /api/tasks/{t}/claim、/start、/submit、/accept、/return | 按负责人、角色、状态、version 共同校验 |
| F03 | POST /api/tasks/{t}/review-requests、/review-opinions | 组长委派、被委派者写意见，最终仍由组长决定 |
| F04/F08 | GET /api/projects/{p}/activities；GET /api/notifications；POST /api/notifications/{n}/read | 分页、去重与接收者校验，不把活动记录当消息队列 |
| F04 | GET /api/projects/{p}/contributions | 按任务与验收事实聚合，不自动评分 |

建议错误：未登录 401，无权限 403 或统一不泄露资源存在性的 404，输入不合法 400，领取或版本冲突 409；业务码说明具体原因。禁止仅靠传入 userId 或客户端声称的角色决定权限。后端直接校验所有项目与任务读写，不仅在 UI 隐藏按钮。

WebSocket 消息包含 eventId、projectId、taskId、type、occurredAt 和最少必要摘要，订阅身份由服务端校验。事务成功后再发更新；第一版可由已提交 Activity 读取并推送，重连时以 HTTP 补查为准，不宣称恰好一次投递。撤销成员关系后应停止其连接接收该项目数据。新事件提醒页面刷新数据，不信任客户端用事件直接绕过业务校验写状态。

本地桥接候选：workspace.open/clone、tree.list、notes.get/set、git.status/diff/identity/branch/commit/fetch/pull/push、ai.configure/chat。每项接口明确参数和结果，只允许已选工作区。Git 进程使用参数数组调用，不拼 shell 字符串；限制协议与参数，路径不能逃逸工作区，Git、模型输出只作数据展示，不能成为执行指令。

## 5 Git 与工作区执行规则

### 5.1 克隆与身份

支持先打开或克隆本地仓库，再登录并绑定协作项目；也支持登录后从项目进入克隆。没有系统登录时不能读取共享项目数据。克隆前检测 Git、地址、目标目录和认证条件；默认只接收 HTTPS GitHub 地址，其他协议后续另行支持。

目标目录要求不存在或为空，不覆盖已有文件。采用 Git 子进程的真实输出显示阶段与能够获取的百分比，不编造全程线性进度。取消时停止自己的进程，保留或明确标记未完成目录，不自动递归清理用户文件；只有确认仓库有效后保存成功绑定。

设置 Git 作者姓名和邮箱默认使用仓库级配置，修改全局配置必须另有用户选择。作者信息影响提交归属，不是推送授权；缺少 GitHub 凭据时采用已有 credential helper 引导授权，不把邮箱当口令。[Git 配置](https://git-scm.com/docs/git-config)、[Git 凭据](https://git-scm.com/docs/gitcredentials)

### 5.2 任务分支与写操作

每任务建议 task/{taskId}-{shortName} 分支，基于已知默认分支或用户确认的基线创建，先检查本地状态。已有关联分支则复用，不重建覆盖；本地有未提交改动时不静默切换到另一任务。分支创建、切换、提交、拉取、推送均提供操作对象确认，并串行化同一工作区的写操作。

提交只处理用户选中文件，不使用无提示的全量暂存；已有暂存区内容与当前选择不一致时阻止并解释，不能为了方便把无关内容提交。支持查看差异、填写说明与取消确认。完成后返回真实提交标识，区分 commit 成功而 push 失败的两阶段结果。

获取远程信息不等于整合；初版 pull 仅在允许条件下使用明确快进策略。遇到工作区脏状态、分叉、无跟踪分支、认证失败或合并进行中等情况，分别解释并停止不适用的动作。不自动执行强推、硬重置、丢弃文件或内容冲突修复。远程在检查后仍可能变化，不能将预检查当成成功保证。[Git push](https://git-scm.com/docs/git-push)

组长初期通过 GitHub 或现有工具检查和合入任务分支；客户端不需第一版内置 PR 创建、审批与合并。系统任务验收状态与远程合并状态独立，不能伪造自动同步。

### 5.3 备注与提交提醒

按工作区和仓库相对路径保存备注，使用原子写或等效机制避免文件损坏；初版不自动跟踪改名，允许新路径重填，旧备注留作失效记录。目录按需加载，`.git` 内部对象不递归显示。

提交验收前可以检查已绑定仓库，提示存在未提交改动或本地未推送提交；未绑定、状态未知、离线等情况显示“无法确认”。这种提示针对仓库状态，不能断言每个改动都属于当前任务，也不擅自阻止验收。手动关联提交标识是后续增强，贡献统计始终以任务与验收为准。

## 7 AI 配置的额外约束

模型地址、模型名、API 密钥按本人配置；先实现一个经过验证的适配器。个人密钥用操作系统支持的本地加密能力，具体 API 按所锁定 Electron 版本验证；不可用时采用仅当前会话保存并明确提示，不降级为明文长期落盘。Windows 本地加密不等于能防同账号下所有恶意程序，不做绝对安全承诺。[Electron safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage)

只发送用户主动输入或确认选取的任务内容，不自动上传整个仓库、`.git`、环境文件或密钥。不记录完整授权头、密钥、模型地址中的凭据；错误信息也要脱敏。AI 返回值作为建议展示，不执行其中命令，不自动发布、分配、验收或调用 Git。草稿进入正常组长发布流程。

AstrBot 为用户指定的未来扩展参考，不复制其插件系统、不承诺 MCP，不将未来研究塞进 0.6。[AstrBot 仓库](https://github.com/AstrBotDevs/AstrBot)

## 8 验证要求

优先验证有业务风险的行为，不为静态文案或简单配置机械堆测试。测试使用本机临时仓库及临时 bare 远程，或明确授权的专用测试仓库，不对真实课程代码做强推或破坏操作。

| 类别 | 必须覆盖的检查 |
| --- | --- |
| 权限 | 非成员读取、组员发布、组员最终验收、跨项目改对象、被移除成员继续请求或订阅 |
| 任务 | 同时领取一人成功；重复提交不重复验收；退回保留负责人和原因；复核不越权；截止显示一致 |
| 事务 | 任务状态与动态同时提交，失败回滚；实时提示不宣称未提交的成功 |
| Git | 克隆成功与失败；非空目录；作者缺失；脏工作区；暂存选择不一致；分叉；push 拒绝；取消和进程失败 |
| 本地数据 | 两个工作区同名文件不串；重启后备注存在；文件改名不错误绑定；不同账号的工作区关联不串 |
| 实时 | 双客户端更新、断线重连补查、重复事件去重、已读独立、后台与彻底退出 |
| AI | 超时、错误返回、密钥不入后端和日志、回复无自动执行、AI 不可用核心仍运行 |
| 交付 | 新 Windows 机器安装、客户端连同一个后端、数据库初始化及迁移、配置无真实密钥 |

## 9 每次交接必须留下什么

每次只推进一个明确功能切片；开始前说明目标版本、功能编号、相关依赖和验收动作。修改已有代码前检查未提交改动，不覆盖其他人的工作。不自动创建额外聊天或调用其他 AI 代理；是否并行开发由实际授权和仓库规则决定。

完成后更新随代码的进度记录，至少包含：日期、版本、F 编号、完成行为、变更文件、执行过的验证与结果、尚未实现或失败项、下一个建议切片。未运行测试说明原因，不写“全部通过”。如果无法完成，只保留可复核成果与真实阻塞，不标记完成。

交接输入示例：

```text
先阅读两份开发文档与现有进度，检查代码实际状态。
本次推进版本：0.3；功能：F03 原子领取。
```
